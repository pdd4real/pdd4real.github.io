Arch Linux 上 Neovim + markdown-preview 实时预览搭建与踩坑全记录

记录一次在 Arch Linux 上为 Neovim 搭建 Markdown 实时预览（markdown-preview.nvim）的完整过程：与本地 Vim 的共存检查、配置落盘，以及四个连环踩坑——从 vim-plug 找不到、Ctrl+S 被终端吞掉、F5 被桌面抢走，到最终那个最隐蔽的「按键静默失败」：预览服务端缺 node_modules。重点沉淀了 headless 模式下的诊断方法论。

背景与目标

本机原本只装了一套 Vim 9.2 + gvim，用 vim-plug 管理插件（~/.vim/plugged），装过 coc.nvim，~/.vimrc 里配了中文编码和 Coc 补全快捷键。目标是：

  • 装一个 Neovim，配好 markdown-preview.nvim，实现编辑 .md 时的浏览器实时预览；
  • 全程不得影响现有 Vim 的配置与 coc.nvim。

环境：Arch Linux、bash、TERM=xterm-256color、Node.js v26.5.1。

方案选型与共存检查

为什么选 Neovim + markdown-preview.nvim

Markdown 编辑器的方案很多（Typora / Obsidian / Mark Text 等），但既然机器上已有 Vim 工作流，最贴合的就是 Neovim + markdown-preview.nvim：同一套 vim-plug、同一个插件目录，两个编辑器共享。

与本地 Vim 的冲突检查

层面 是否冲突 说明
二进制/包 不冲突 neovim 与 vim/gvim 是 Arch 官方源独立包，互不覆盖
配置 有一个坑 Neovim 走 XDG 路径（~/.config/nvim/），不回退读 ~/.vimrc；但前提是必须建独立 init.vim，否则 Neovim 会回退去 source ~/.vimrc（带着 coc 配置），不干净
插件 不冲突 vim-plug 两个编辑器通用，可以共享同一个 ~/.vim/plugged 插件目录
依赖 已满足 coc.nvim 和 markdown-preview 都需要 Node.js

坑一：E117: Unknown function: plug#begin

根因：vim-plug 的 plug.vim 在 ~/.vim/autoload/ 下，而 Neovim 的运行时路径不包含 ~/.vim（XDG 化），自然找不到 plug#begin 函数。

坑二：Ctrl+S 没反应

现象：键位明明绑定了（:verbose nmap <C-s> 能查到），但按了毫无反应。

根因：Linux 终端把 Ctrl+S 当作流控命令 XOFF（暂停屏幕输出），根本不会传给 nvim。这是 Vim 用户的老熟人坑。

解决：关掉终端流控，或换个键：

更稳妥的做法是干脆换键（见下文 Ctrl+P）。

坑三：F5 被桌面抢走

现象：改成 F5 后依旧没反应。

根因：笔记本的 F5 是屏幕亮度键，被桌面/硬件层截走，同样到不了 nvim。

结论：选键要避开三类：终端流控键（Ctrl+S/Q）、桌面媒体/功能键（F5~F8）、Vim 自身语义重要的键（Ctrl+O 跳转等）。Ctrl+P 在终端是普通控制字符、桌面不抢、Vim 默认无冲突，是最省心的选择。

坑四（最隐蔽）：预览按键静默失败 —— 缺 node_modules

现象：插件装好了、键位绑好了、插件也加载了，但按任何预览键都毫无反应、不弹浏览器、状态栏也不报错。

根因：预览服务端是插件 app/ 目录下的一个 Node.js 服务。mkdp#util#install() 拉下来的 app/ 只有编译产物，node_modules 依赖缺失。服务起不来，而插件对启动失败是「静默」的——这就是为什么前面一切检查看起来都正常。

诊断方法论（重点）

这次最值得沉淀的不是某个命令，而是**「按键无响应」这类静默故障的分层排查法**：

  1. 确认插件有没有装上 / 有没有加载

  2. 确认键位有没有绑定

  3. 确认配置有没有干净加载

  4. 直接触发核心函数，把静默错误炸出来

    这一步把「没反应」从玄学变成可复现的错误信息，是本次破案的关键。

  5. 确认服务真的起来了（不是端口探测，而是看进程 + 端口）

    注意：预览服务随 nvim 会话退出而退出，所以要在 nvim 存活时查。

\mp 切换预览
\ms / Alt+s 停止预览

Arch Linux × Windows 跨设备远程桌面搭建全记录

记录一次完整的「Arch Linux (KDE Plasma 6.7.3, Wayland) ↔ Windows 11」双向远程桌面搭建过程：从方案选型、双向配置，到踩过的两个 KDE 上游 bug、若干 Windows 侧坑位，以及最终的连接调优。文中 IP 均已脱敏，实际使用请替换为你的真实地址。

一、背景与需求

  • Arch 本机：KDE Plasma 6.7.3，Wayland 会话，主机名 <ARCH_HOST>，内网 IP <ARCH_IP>
  • Windows 机器：Windows 11 25H2，ProfessionalWorkstation 版本，内网 IP <WIN_IP>
  • 需求：跨设备远程桌面，两个方向都要能连

架构选型：

方向 服务端 客户端
Windows → Arch krdp（Plasma Wayland 原生 RDP 服务器） Thincast Remote Desktop Client
Arch → Windows Windows 原生 RDP Host KRDC（KDE RDP 客户端）

选 krdp 的原因：它是 KDE Plasma 对 Wayland 的原生 RDP 实现，随桌面预装，无需额外服务。但先要接受它的三条限制：

  • 仅支持 NLA 认证
  • 无音频、无剪贴板共享
  • 登录界面 / 锁屏状态下不可访问

二、方向一：Windows → Arch（krdp）

2.1 服务端配置

  1. 打开 System Settings → Remote Desktop（远程桌面 KCM）
  2. 在 Server 区域选择要授权登录的用户（这里选了 eliopan）
  3. 勾选 Start on login（autostart），保证开机后自动监听
  4. 点击 Apply

krdp 默认监听 3389 端口。证书为自签名，存放在 ~/.local/share/krdpserver/（krdp.crt / krdp.key），客户端首次连接会提示不受信任，需手动确认。

2.2 Bug 一：mstsc 无法连接（KDE Bug 511557）

用 Windows 自带的 mstsc 连接，输入 IP 和凭据后，进度走到一半报 PostConnect failed，无法进入桌面。

这是上游已知的兼容性问题（KDE Bug 511557），至今未修复，本质是 mstsc 与 krdp 在连接握手阶段不兼容，与证书、密码无关。

解法：放弃 mstsc，改用基于 FreeRDP 的 Thincast Remote Desktop Client 作为 Windows 端客户端。新建连接时填 <ARCH_IP>:3389，勾选允许保存凭据。

2.3 Bug 二：PAM 认证失败，黑窗闪退（KDE Bug 521776）

Thincast 上第一次连接会弹出自签名证书警告，点继续后弹出一个黑框直接闪退，Arch 端也没有任何授权确认框，仿佛连接根本没到达认证阶段。

排查过程：

  1. 先在 Arch 本地验证密码本身没问题： 密码输入正确，确认不是密码错误。
  2. 查看 krdp 服务日志，发现关键报错：
  3. 查看 systemd 服务文件，定位根因： 发现其中有 NoNewPrivileges=true。

根因是上游 KDE Bug 521776：NoNewPrivileges=true 阻止了 unix_chkpwd 提权校验密码，导致 PAM 认证必然失败。上游在 6.7.2 已通过移除该设置修复，但 Arch 的 6.7.3 打包仍残留该设置，所以必须手动覆盖。

重启后重新用 Thincast 连接，授权框正常弹出，认证通过，桌面成功显示。

2.4 附带坑：pam_faillock 账户锁定

排查过程中反复认证失败，累计触发了 pam_faillock 账户锁定：

  • 默认策略 deny=3、unlock_time=600（配置文件 /etc/security/faillock.conf 为空即用默认值）
  • 由于 /etc/pam.d/system-auth 的 preauth 段包含了 faillock，连 sudo 都一并被锁——表现为 sudo 输入正确密码也报认证失败

处理方式：等约 600 秒自动解锁（可查看锁定剩余时间确认），解锁后清掉计数：

3.2 大坑：3389 无 LISTEN，重启才恢复

排查时遇到了一个非常迷惑的现象：

  • sc query TermService 显示服务 RUNNING
  • fDenyTSConnections 注册表为 0x0，配置正常
  • 防火墙的远程桌面规则全部启用
  • 但 netstat -an | findstr :3389 无任何返回
  • qwinsta 也没有 RDP-Tcp 监听器
  • 尝试 net stop TermService 被拒绝，无法重启服务

结论：服务状态与配置长时间不同步，属于偶发问题。最终靠 Settings 里先关闭再开启远程桌面，然后重启 Windows 解决——重启后 netstat 正常出现 LISTEN，qwinsta 也能看到 RDP-Tcp。

教训：遇到「服务显示正常但端口无监听」时，先不要盲目去改注册表和防火墙，先重启再谈排查。

3.3 KRDC 连接配置

Windows 端就绪后，用 KRDC 连接 <WIN_IP>:3389。连接对话框中有几个关键填写项：

字段 填什么
服务器 / Host <WIN_IP>:3389
username 用户账号名（不是电脑名称）
domain 留空

username 到底填什么（这是最容易踩的）:

  • 电脑名称（主机名，如 DESKTOP-XXXX）是错的——那用于服务器地址，不是凭据
  • 填 Windows 的登录账号名；不确定时在 Windows 上执行：
  • 微软账户登录则填完整邮箱，domain 依旧留空
  • 若本地账户名与其他东西冲突，可在用户名前加 .\（如 .\用户名）强制指本机账户

另外，连接过程中 KRDC 曾出现卡死无响应的情况，直接 pkill -f krdc 重开即可，也可用朴素参数（关闭音频、不共享媒体、避免全屏）降低客户端出问题的概率。

3.4 连接慢：Windows 反向 DNS 解析

连接成功后观察到一个新问题：netstat 显示 Windows 的 3389 与本机端口已建立 TCP 连接（网络层是通的），但 KRDC 要等很久才进桌面。

根因：Windows 的 RDP 服务器收到连接后，会对客户端 IP 做反向 DNS 解析。家用路由器没有给设备配置主机名解析，这次反向查询要一直等到超时（默认约 30 秒）才放弃，于是卡在进桌面之前。

3.5 桌面布局与缩放不一致

远程桌面显示的快捷方式摆放和缩放大小与 Windows 原机不同——这是 RDP 的固有行为：远程会话是全新会话，其分辨率由客户端决定，不是物理显示器。分辨率一变，Windows 就重新排布图标、重新计算 DPI 缩放。

解法：让远程会话尽量贴近原机：

  • 确认 Windows 物理显示器的原生分辨率（如 1920×1080）
  • 在 KRDC 连接设置里把 resolution 设为与该分辨率一致 ← 关键
  • desktop scale factor 保持 100%（不想放大就 100%）
  • device scale factor 保持 100%——它管的是本机（Arch）高分屏的适配，与「Windows 布局是否一致」无关；只有本地是 2K/4K 且开了系统缩放时才需要动

3.6 RDP 会话隔离：物理桌面看不到

连接后会发现：在 Windows 物理屏幕上刚打开的程序，远程会话里看不到。

原因：RDP 是独立会话。你在物理屏幕（控制台会话）打开的东西，活在控制台会话里；RDP 连进去是另一个隔离的会话，两边桌面互不可见——你看到的是远程会话自己的桌面，不是物理屏幕的实时画面（且你连入时物理屏通常还会自动锁定）。

这是 RDP 的固有机制，不是故障。如果目标是「直接看/操作物理桌面上已经开着的东西」，两个方向：

  • 连接控制台会话：mstsc /v:<WIN_IP> /admin，Linux 端可用 xfreerdp 加 /admin 参数
  • 改用 RustDesk 这类「屏幕控制」工具，它才是真正接管物理桌面

六、跨网络方案：Tailscale

上面的方案只能在家用，出门就没法连了——因为 Windows 在路由器 NAT 后面，公网摸不到它的 3389。这里用 Tailscale 打通跨网络 RDP。

6.1 Tailscale 是什么

Tailscale 基于 WireGuard 建立加密隧道，给每台加入的设备分配一个虚拟内网 IP（100.x.x.x），所有设备之间通过这个虚拟 IP 直接通信，底层是 WireGuard 点对点加密，无需暴露任何公网端口。免费方案支持 100 台设备，对个人使用完全够用。

KRDC 用 Tailscale IP 连 RDP 的逻辑跟局域网完全一致——客户端根本不关心你给的是物理 IP 还是虚拟 IP，只要网络层通就行。

6.5 原理简述

KRDC 不需要任何特殊配置——它只知道要连 100.a.b.c:3389 这个 RDP 端点，至于数据包怎么过去的是 Tailscale 的事。底层的 WireGuard 隧道保证了跨公网也能端到端加密通信，同时不用在路由器上开放任何端口。

本文覆盖局域网（一至五节）与跨网络（第六节）两个场景。自托管 RustDesk 是另一种备选方案，需要额外维护一台中继服务器，在本文不展开。
